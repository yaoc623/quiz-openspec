# Design

## Context

參見 proposal.md 的 Why。服務使用單一 Node.js 程序保存 `QuizState`，透過 Socket.IO 將角色專用狀態快照推送給既有與新連線。老師以 HTTP 控制匯入、開始及結束；目前答題資料有伺服器接收時間和每題順位。

## Goals / Non-Goals

**Goals:**

- 讓伺服器保存本輪計時設定、開始時間與期限，控制時間到自動結束。
- 由既有角色狀態快照傳遞倒數與排行榜，學生端不取得搶答中的全班排行榜。
- 讓開始新活動清除本輪期限、計時偏好及排行榜來源資料，預設回到不限時。

**Non-Goals:**

- 保存跨服務重啟的計時或排行榜資料。
- 為單題設定獨立期限、暫停倒數或延長期限。
- 將排行榜或計時資料寫入 Google 試算表。

## Decisions

### 伺服器期限為唯一計時來源

老師在準備階段設定 `unlimited` 或秒數。開始時伺服器記錄活動開始時間及（若有限時）絕對期限，並排程期限到達時呼叫與手動結束相同的狀態轉換。手動結束或開始新活動會清除該排程。計時設定在準備階段才可變更；新活動重設為不限時。

替代方案：由瀏覽器各自建立計時器會因背景分頁節流、重新整理或裝置時鐘不同而產生偏差，也無法可靠地自動結束伺服器活動。

### 快照攜帶伺服器時間錨點

每次狀態快照包含期限、伺服器產生快照的時間及剩餘毫秒數。瀏覽器以收到快照時的本機單調時鐘推進顯示值，並以伺服器定期推送的剩餘時間校正；重新連線取得新的時間錨點，不沿用瀏覽器儲存值。伺服器排程仍負責真正結束活動，瀏覽器倒數只負責顯示。

替代方案：客戶端以 `Date.now()` 單獨計算期限會受裝置時鐘錯誤影響；每秒廣播完整狀態則不必要地增加事件與畫面重繪。

### 有效提交資料計算排行榜

排行榜依每題目前排名第一的有效答案計分，一題一分，題組沿用題號視為一題。平分計時採合理預設：每組所有有效提交的實際接收時間減去本輪開始時間後加總，較短者優先；仍相同時組別編號較小者在前。公平模式後續會另以判定時間挑選成功者，但排行榜的時間平手規則仍使用實際送出時間。

替代方案：以瀏覽器時間計算送出時間會使不同裝置時間無法比較；只靠分數排序會讓同分名次不穩定。

### 排行榜由伺服器依角色裁切

老師的快照在搶答中與結束後包含排行榜；學生快照在搶答中不包含全班排行榜，只有結束後才附上同一份排行榜。每次有效提交、手動結束、計時到期及新連線都從伺服器目前資料計算狀態。

替代方案：只在前端隱藏排行榜仍會把全班排名傳給學生；依角色裁切快照沿用現有資料隔離模式。

## Risks / Trade-offs

- [服務主機休眠或程序停止時，JavaScript 排程可能延後] → 每次顯示/狀態計算都依期限重新算剩餘時間；排程喚醒時立即結束，不依賴累加 tick 數。
- [有限時狀態每秒更新會增加 Socket.IO 廣播] → 僅在有限時的搶答期間推送簡短計時事件，其他狀態變更仍使用完整角色快照。
- [累計提交時間可能受答題數量影響] → 固定以本輪開始時間為基準，累計所有已接受的實際提交時間，並將此規則記入規格與介面排序說明。

## Migration Plan

1. 在活動狀態加入計時設定、開始時間和期限，並以伺服器排程管理自動結束。
2. 加入老師準備階段計時設定、共用倒數顯示與重新連線校正。
3. 由伺服器計算分數及同分順序，依角色提供即時或結束後排行榜。
4. 擴充狀態單元、Socket.IO 整合及瀏覽器介面測試，執行完整測試並啟動服務驗收。
5. 回退時移除計時與排行榜欄位和控制；既有題目、作答、試算表匯入/回寫格式不變。
